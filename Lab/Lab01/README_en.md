# Lab 1: End-to-End Requirement Compilation and Continuous Evolution

This lab uses the Ticket Booking Demo to observe how an agent turns requirements into interfaces, tests, and a runnable application, and continuously corrects the implementation through internal training tests and external platform validation tests.

## Learning Objectives

After completing this lab, you will be able to:

- Understand the traceability relationship among requirements, interfaces, tests, code, and run results;
- Distinguish between Training Test Case and Validation Test Case;
- Handle internal test failures and external validation failures;
- View the code, nodes, tests, and Preview associated with different historical versions;
- Modify existing requirements, add incremental requirements, and observe the agent's incremental processing.

## 1. End-to-End Workflow

### Start the Demo

1. Sign in to the platform at `arc-bench.com` and click **Quick Start**.
2. Select the Ticket Booking task and start the Demo.
3. Observe the three stages:
   - Stage 1: Prepare the workspace and agent;
   - Stage 2: Design, generate tests, and implement features according to the requirement nodes;
   - Stage 3: Perform final validation using platform tests.
4. Wait for the automatic process to complete the first build and pause automatically. All operations after this point are performed manually by the learner.

### A Traceable Path: From Search Requirement to Validation Result

Follow the path below. You do not need to open all nodes at the same time:

1. Select `REQ-2.1` in Canvas, expand Requirement Details, and locate the scenario where a search is rejected when the origin and destination are the same.
2. In Traceability, view the interface chain associated with this scenario: `UI-REQ-2.1-HOMEPAGE-SEARCH-SUBMIT` -> `API-FE-SEARCH-TICKETS` -> `API-BE-SEARCH-TICKETS` -> `FUNC-BE-SEARCH-TICKET-QUERY`.
3. Click the file source of `FUNC-BE-SEARCH-TICKET-QUERY`, open `backend/src/services/search_service.js`, and confirm that it normalizes the search criteria and queries train services.
4. View the Training Test Case for the same scenario: `REQ-2.1::Unit::001::REQ-2.1-SEARCH-UNIT`. It verifies search-input normalization and date preservation.
5. Open Test Results and click the external Validation Test Case `REQ-2.1: reject a same-city search without opening a result list`. The platform returns to the same requirement scenario and displays the current pass/fail status of the external test.
6. In Live Preview, enter `Shanghai` and ` shanghai ` and submit the search. Then return to Files and the test source to compare the complete path from user behavior to interface, internal test, and external acceptance.
7. Finally, open Commit History and select the commit related to this feature to view its Diff. Confirm that the requirement, tests, and implementation form one traceable path.
8. Return to the normal search scenario and select a train card. Observe how the `REQ-2.2` train-selection scenario reuses `API-FE-SEARCH-TICKETS` and how the train card is rendered in the search results page files.
9. Enter the Booking page from the search results, select `REQ-3.2`, and view the call relationships among `UI-REQ-3.2-BOOKING-FORM`, `FUNC-BE-CREATE-BOOKING-RECORD`, and `DB-BE-BOOKINGS-INSERT`.
10. Under this requirement, view the Training Test `REQ-3.2::Unit::001::REQ-3.2-UNIT-BOOKING-VALIDATION` and the external test `REQ-3.2::scenario-1` together. Compare the internal assertions with the user-visible booking confirmation result.
11. Complete one flow from search through train selection to booking submission in Live Preview. Then use Files and Test Results to review the same path.

The panels in this path have the following responsibilities: Requirement Details explains what needs to be done; Traceability explains which interfaces and tests support it; Files shows what was actually written; Live Preview shows what the user saw; and Test Results shows how the platform evaluates it.

### Distinguish the Two Test Types

| Type | Meaning in this lab | Can the agent modify it? |
| --- | --- | --- |
| Training Test Case | A unit, integration, or internal end-to-end test generated by the agent during development to guide implementation | Yes. It can be added, modified, and re-run. |
| Validation Test Case | An external Playwright acceptance test saved in advance by the platform to independently evaluate the final application | No. It cannot be modified. |

Core principle: Do not make the results green by modifying a Validation Test Case. When an external test fails, return to the requirement and Training Test Case to find the cause.

## 2. Interactive Repair

### Part A: Failed Training Test Case

After the first automatic build is complete, the Demo pauses with two failed internal tests preconfigured.

1. In **Traceability**, find `REQ-2.1::Integration::003::REQ-2.1-SEARCH-RESULTS-PAGE`.
2. Click **Re-run TDD** and observe the interface refresh to the repair version for this test.
3. Review the new Commit, file changes, and Preview. Confirm that the internal test for the search results page passes.
4. Find `REQ-3.2::Unit::001::REQ-3.2-UNIT-BOOKING-VALIDATION`.
5. Click **Re-run TDD** again and observe the repair version for the second test.

In real development, when internal tests continue to fail, you can use either of two strategies:

- Continue iterating with the same model for several rounds and let it gradually correct the implementation based on the failure logs;
- Create a new commit and select a more capable model, then compare completion quality, time, and cost.

The Demo's **Re-run TDD** replays this iteration using preset snapshots. After completing this part, the interface remains on the repair result for the second internal test.

### Part B: Failed Validation Test Case - Insufficient Internal Test Coverage

The first external failure comes from `REQ-2.1::scenario-7`: when the origin and destination are the same after ignoring letter case and whitespace, the application should reject the search. The original internal test only checked whitespace removal and did not cover the same-city search rule.

1. Open **Test Results** and click the failed test.
2. Confirm that Canvas automatically selects `REQ-2.1` and highlights only `scenario-7`.
3. In **Traceability**, click **Add Internal Test**.
4. Confirm the new test and observe that it appears and remains failed.
5. Review the test assertions. They check case normalization, leading and trailing whitespace, and same-city rejection together, so their assertion strength is higher than that of the original test.
6. Click **Re-run TDD** for the new test and observe the implementation repair and refreshed test results.
7. Confirm that both the new Training Test Case and its corresponding Validation Test Case pass.

This part demonstrates that when internal test coverage is insufficient or assertions are too weak, you should first add a test that accurately expresses the requirement scenario, and then repair the implementation.

### Part C: Failed Validation Test Case - Incorrect Internal Test

The second external failure comes from `REQ-3.2::scenario-1`. The requirement allows 6-30 ASCII letters, digits, or hyphens, but the original internal test incorrectly required an 18-digit number.

1. In **Test Results**, click the failed test.
2. Confirm that Canvas highlights `REQ-3.2::scenario-1` and locate the incorrect internal test.
3. Click **Edit** next to the internal test and compare the requirement contract before and after the change.
4. Save the change and observe that the corrected test still fails because the application implementation has not yet been repaired.
5. Click **Re-run TDD** and observe the implementation repair and refreshed test results.
6. Confirm that the implementation now accepts valid identification numbers, and that both the corrected internal test and the corresponding external test pass.

This part demonstrates that an incorrect Training Test Case must be corrected. The product implementation must not be changed to satisfy an incorrect assertion.

## 3. Version Rewind and View Switching

First, in **Commit History**, select the records corresponding to "identification number repair completed" and "requirement change completed", then use **View Git Diff** to compare changes to the requirements, tests, and implementation. This operation only switches the diff view and does not change the current Demo progress.

After completing the entire lab, select an earlier version and execute **Rewind to This Commit**. Observe:

1. Canvas node states are restored to that version;
2. Files displays the code and tests from that version;
3. Traceability restores the interface and test relationships from that point in time;
4. Live Preview switches to the website corresponding to that historical version;
5. Test Results displays the validation results for that version.

Rewinding discards the Demo history after the current pointer, so it is recommended that you do this last and select only one target version. Rewinding changes only the current Demo pointer for your user and does not affect other users. To compare the complete path again, restart the Demo.

## 4. Incremental Compilation

### Part D: Modify the Existing Requirement `REQ-2.2`

Incremental change: when the user returns to the search results from the booking entry point, the origin, destination, date, result list, and previously selected train must be preserved, and no order may be created.

1. In the version where the current feature is complete, select `REQ-2.2` and click **Edit**.
2. Review the fixed requirement diff and save it. Observe that the requirement status changes to Pending.
3. Confirm that `REQ-2.2` becomes Pending and that its old internal tests and associations are removed. The application temporarily remains the old version.
4. Click **Continue** and observe new interfaces and internal tests being generated. The tests fail initially.
5. Click **Continue** again and observe the return-to-search-results and context-restoration features being completed. Tests for both the new and old rules pass.
6. Verify **Back to results** in Live Preview.

This demonstrates incremental compilation after a requirement change: first invalidate the old evidence, then redesign the interfaces and tests, and finally modify the affected implementation.

### Part E: Add the New Requirement `REQ-3.4`

Incremental change: add "My Orders", which displays only the current logged-in user's orders and supports an empty state and an unauthenticated-user guard.

1. Select the parent node `REQ-3` in the requirement tree.
2. Click **Add child**, use the preset content to add `REQ-3.4`, and observe the new node.
3. Confirm that the new node is Pending and initially has no interfaces, tests, or implementation.
4. Click **Continue** and observe the new requirement's interfaces, tests, and implementation appear.
5. Review the new order-list page, query API, account-isolation logic, and three internal tests.
6. Open **My Orders** in Live Preview and confirm that the new external tests pass in Test Results.

## 5. Completion Checklist

At the end of the lab, you should be able to observe all of the following:

- The automatic build pauses when complete, and subsequent teaching actions are triggered by the learner;
- The two failed Training Test Cases pass after being re-run;
- One external failure is repaired by adding and strengthening an internal test;
- One external failure is repaired by correcting an incorrect internal test;
- `REQ-2.2` completes its requirement change, redesign, and implementation;
- `REQ-3.4` completes its requirement addition, tests, and implementation;
- Commit History, Traceability, Files, Live Preview, and Test Results consistently display the same current version.

Complete teaching path: automatic build and pause -> repair two internal tests -> add an internal test and repair the implementation -> correct an incorrect internal test and repair the implementation -> modify `REQ-2.2` and recompile -> add and implement `REQ-3.4`.
