This lab compares two Registration API implementations generated by the same model: Direct preserves the implementation generated by the model on its first attempt, while TDD starts from an identical copy and gradually repairs the code based on feedback from executable tests.

> Complete all configuration in the first part before class. Model calls may incur charges, so use credentials provided by the instructor or credentials you are authorized to use.

## I. Pre-Class Environment Setup

This section supports both macOS and Windows. No command-line version-control tools are required. Install Node.js and Visual Studio Code in order, then open the `Lab02` folder separately in VS Code.

### Step 1: Install Node.js 24

The Node.js installer also installs the npm package manager required by this lab.

#### macOS

1. Open the [official Node.js download page](https://nodejs.org/en/download) in a browser.
2. Confirm that the page is set to **v24.x.x (LTS)**. Do not select Current or another version.
3. In the prebuilt downloads section, select:
   - Operating system: **macOS**;
   - Processor: choose **ARM64 / Apple Silicon** for a Mac with an M1, M2, M3, M4, or newer Apple chip; choose **x64 / Intel** for an older Intel Mac;
   - Download type: **Installer (`.pkg`)**.
4. When the download is complete, double-click the `.pkg` file.
5. In the installer, click **Continue**, **Agree**, and **Install** in order. Enter your computer password or use Touch ID if prompted.

#### Windows

4. When the download is complete, double-click the `.msi` file. If Windows asks whether to allow the app to make changes to your device, click **Yes**.
5. In the setup wizard, click **Next**, accept the license agreement, and keep the default installation location and components. Do not deselect Node.js, npm, or the option to add Node.js to PATH.
6. Click **Install**, then click **Finish** after installation completes.

## II. In-Class Workflow

The lab contains two scenarios: Registration API and Registration GUI. Each scenario is divided into Act 0–5. The program pauses at the end of every Act. Read the terminal output and press Enter to continue; you do not need to re-enter the command.

### 1. Understand the Comparison

First, clarify these three concepts:

- **Direct**: The first implementation generated directly by the model from the task. It is not modified afterward.
- **TDD**: A copy of the same Direct implementation, repaired according to executable tests generated by the model.
- **Validation**: Independent validation prepared in advance by the instructor. It evaluates the result but does not provide failure details to the model.

Direct and TDD use the same task, model, and initial code. The only difference is that the TDD branch has a test-feedback loop.

### 2. Run the Registration API Experiment

Run the following command in the VS Code terminal:

```bash
npm run demo:api
```

Follow the terminal prompts and observe the following steps:

1. **Act 0 — Review the task**: Read the Registration API task requirements and experiment structure.
2. **Act 1 — Generate the Direct implementation**: The model generates `register.ts`, and the program simultaneously copies it as the starting point for TDD.
3. **Act 2 — Check the Direct result**: Use instructor validation to check the unrepaired Direct implementation and record the results by category.
4. **Act 3 — Generate train tests**: The model generates executable Vitest tests. The tests are first checked against the instructor's reference implementation and are frozen for use with TDD only after they pass completely.
5. **Act 4 — Establish Red and repair toward Green**: Run the training tests on the TDD copy and first observe Red. Then let the model repair the code based on test feedback until it reaches Green or the repair limit.
6. **Act 5 — Compare Direct and TDD**: Run instructor validation again, then compare the final results, elapsed time, and model-call information for Direct and TDD.

### 3. Run the Registration GUI Experiment

Confirm that `npm run setup:browsers` has already been run, then execute the following command in the VS Code terminal:

```bash
npm run demo:gui
```

The GUI workflow automatically opens a browser when a page needs to be observed. Keep the terminal window open and switch between the browser and terminal. You can fill in and submit the registration form, test error messages and the password visibility button, and narrow the window to observe the responsive layout. After inspecting the page, return to the terminal and press Enter to continue.

Follow the terminal prompts and observe the following steps:

1. **Act 0 — Review the task**: Read the registration page requirements and view the reference page provided by the instructor. The reference page is only for understanding the task and is not provided to the model.
2. **Act 1 — Generate the Direct implementation**: The model directly generates the single-file `index.html` page, and the program copies the same page as the starting point for TDD.
3. **Act 2 — Check the Direct result**: Instructor Playwright validation checks the Direct page. The browser opens the page so you can operate it yourself and compare the result with the category scores in the terminal.
4. **Act 3 — Generate train tests**: The model generates a Playwright train suite. The program first runs it against the instructor's reference implementation. If a test fails, the failure context is sent to the model for repair. The suite is frozen only after the complete suite is GREEN on the reference implementation.
5. **Act 4 — Establish Red and repair toward Green**: The frozen tests establish Red on the Direct copy. The model modifies the TDD page over successive rounds based on the visible test failures until the train suite is Green or the repair limit is reached.
6. **Act 5 — Compare Direct and TDD**: Instructor validation independently evaluates the final TDD page. The browser opens the repaired page, while the terminal compares the Direct/TDD scores and summarizes the time and token usage for each model call.

If the browser does not open automatically, copy the page address from the terminal output into a browser. If the terminal reports that Chromium is missing, run the following command again:

```bash
npm run setup:browsers
```

For unattended batch model evaluation, you can disable the pause after each Act and automatic browser opening:

```bash
npm run demo:gui -- --no-interactive --no-open --model deepseek-v4-flash
```

At the end of each model stage, the terminal displays the elapsed time, number of requests, and input, output, and total tokens for that stage. At the end of the entire run, it outputs a `MODEL_RUN_SUMMARY` JSON line. Automation scripts can parse this line directly, and the complete data is also saved in that run's `result.json`.

### 4. Summarize Multiple GUI Runs

After running batches, you can summarize the GUI results directly:

```bash
npm run summarize:runs
# Only include results after a specific run ID
npm run summarize:runs -- --after 20260910T162353Z
```

In the table, a successful run is defined as one where the train suite on the reference implementation is fully GREEN, the final TDD train suite is fully GREEN, the workflow result is `GREEN`, and the number of hidden validation tests passed by TDD is higher than the number passed by Direct. Failed runs count toward Attempts and the success-rate denominator. The averages for tokens, model time, Direct/TDD validation, and improvement are calculated only from successful runs, making the table suitable for direct use in classroom comparisons.

### 5. Compare and Discuss

Use the Act 5 results as the basis for discussion:

- Which behaviors did TDD repair compared with Direct? Which validations still failed?
- Did the model-generated training tests cover the requirements that actually mattered?
- How did test quality limit the quality of the final implementation?
- How much model-call, time, and token cost was required for the quality improvement?

A single experiment result does not prove that TDD is always better than Direct. Draw conclusions from the actual results shown on screen. Do not modify instructor validation merely to obtain an all-green result.

The current code and tests generated by the experiment are located in `workspace/api/` or `workspace/gui/`. The complete record of each run is stored in `runs/`. These directories may contain model-generated code, so do not run or extend them in an environment containing unrelated sensitive information.
